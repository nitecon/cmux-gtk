# Project configuration and actions

The active parity goal includes project actions, workspace definitions, command execution, palette discovery and configurable UI actions. The first implementation provides read-only resolution through `cmux project-actions --directory PATH` (JSON output, no running app required). Explicit local command execution is available through `cmux project-run ACTION --workspace UUID --fingerprint HASH`; discovery never executes commands.

The resolver reads global `$XDG_CONFIG_HOME/cmux/cmux.json` (falling back to `$HOME/.config/cmux/cmux.json`) and searches upward from the canonical requested directory for the nearest project file. At each directory `.cmux/cmux.json` wins over `cmux.json`. The winning project action replaces the entire global entry with the same ID; unrelated global actions remain. Each returned action retains its complete raw definition and winning source path.

This matches `findCmuxConfig`, `loadAll`, and `mergedActionEntries` in the inspected upstream `Sources/CmuxConfig.swift` at e36b8e8632a414e2982185f8dae4002a98be2b53. That implementation uses nearest-project action resolution plus global fallback; its separate notification-hook lookup walks the ancestor hierarchy. The directory-actions dogfood README describes broader ancestor inheritance, so do not infer action merging from that README alone.

Reads require regular files, follow symlinks and use the platform nonblocking-open helper to avoid waiting on FIFO peers. Each file is limited to 256 KiB; lookup visits at most 64 directory ancestors; the final registry contains at most 256 actions with nonempty IDs bounded to 128 bytes. Invalid selected files produce errors instead of silently running a lower-precedence file. JSON structure and the typed action schema are validated. Other configuration sections are not yet applied.

Next steps are typed command/builtin/agent/workspace/workspaceCommand definitions and explicit target semantics, shared GTK-worker/RPC resolution, reviewable trust for project-defined execution, palette integration, action execution and launch-layout support. Existing launch/resume ownership should be reused. Merely entering a directory or listing actions must never execute project commands. Remote project files require remote reads through their workspace transport; local filesystem resolution is not a substitute.

Actions coverage includes actual directory precedence and source provenance. Strict workspace Clippy passes; runtime execution remains in GitHub Actions. Generated command completions and the man page follow the shared CLI schema.

Action records now include typed `intent` and `target` alongside the raw definition. Command, agent, builtin, workspaceCommand, workspace and metadata-only families use upstream explicit-type/inference order. Command text remains literal; required executable strings reject blank/NUL/oversize values. Targets accept currentTerminal and newTabInCurrentPane, defaulting to a new sibling tab. Presentation strings, booleans and keyword arrays have explicit type/size checks. Workspace payloads remain raw objects and builtin names are not yet resolved to the Linux capability catalog; those are not validated execution plans. Tests cover literal command preservation, explicit-type precedence, targets and malformed executable fields. Strict Clippy passes; Actions runtime results are pending.

Builtin intent now uses a closed enum with upstream canonical IDs and spelling aliases, rejecting unknown names. The catalog retains agent-chat, cloud, mobile and simulator identities alongside workspace/terminal/browser/split actions. Recognition is not an execution-availability claim: handlers and platform adaptations remain outstanding. Alias/unknown-name tests compile under strict Clippy; Actions runtime execution is pending.

Workspace intent now contains typed name/cwd/color/setup/environment and recursive layout data. Layouts accept either a pane with at least one surface or a horizontal/vertical split with exactly two children, rejecting mixed pane/direction nodes. Ratios default to 0.5 and clamp to 0.1–0.9 like upstream. Validation bounds depth to 32 and total surfaces to 128; each environment has at most 64 identifier keys and 64 KiB of bounded NUL-free values. Surface terminal/browser/project types, optional focus booleans and launch strings are validated. Project-surface rendering, named-color resolution, restart behavior, managed-environment precedence and actual launch application remain execution gates. Strict Clippy passes; Actions tests cover mixed layouts, ratio behavior and invalid nodes/environment.

`cmux project-actions --workspace UUID --json` now calls `project.actions.list`. An omitted RPC workspace selects the current workspace; CLI inspection without --workspace remains local/offline, and --directory conflicts with --workspace. GTK captures the target UUID and local terminal CWD through the same helper used by Git metadata. Two admitted blocking readers share a five-second response deadline; a started filesystem read retains its permit on timeout/cancellation and may outlive the response. Results describe the captured workspace/directory rather than silently switching targets if focus or CWD changes. Remote reads remain explicitly unsupported. Resolution emits trace/workspace/duration/outcome without config contents. Actions coverage checks background lookup, no command execution, source changes after terminal cd and unchanged focus. Strict Clippy and Python syntax checks pass; runtime verification is pending.

Resolved actions now include a SHA-256 fingerprint over a versioned tuple of captured directory, source path, action ID and complete raw definition. This lets the forthcoming execution path reject a changed action or execution context after inspection. It is a change detector, not an authorization credential, stored trust or permission to execute. Tests verify command/target/source/ID/directory changes invalidate it. Strict Clippy passes; Actions execution is pending.

Explicit command execution now re-reads configuration off GTK under the shared two-reader admission limit and five-second deadline. `project.actions.run` requires action_id and fingerprint, accepts an optional workspace_id (default current), and rejects changed definitions, directory context or selected surface before submitting input. CLI callers explicitly request execution; fingerprints provide change detection rather than persistent trust. Only local command intents are executable in this checkpoint.

The default newTabInCurrentPane target opens a selected sibling terminal in the captured canonical directory. A separate `/bin/sh -c` evaluates the command unchanged, then an interactive shell remains; subsequent ordinary tabs retain their original launch defaults. currentTerminal submits literal text and a carriage return to the existing terminal. Execution selects its target workspace. The response contains workspace_id, surface_id and status=submitted, which does not report process completion or exit status. A payload-free project.actions.run event records trace, workspace, surface and submission duration. Config inspection and failed fingerprint checks do not select or launch anything.

Actions coverage now checks stale-fingerprint rejection with no file or focus effects, followed by successful new-tab execution in the reviewed directory. Local Clippy and syntax checks pass; runtime verification remains pending Actions. Persistent trust, palette confirmation, other action families, remote configuration and workspace layout application remain within the active parity goal.
